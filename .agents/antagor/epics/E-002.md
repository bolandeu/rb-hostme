## Problem

A target deploy writes straight into the live folder. A dropped connection, a full disk or an interrupted run leaves old and new files mixed on a site the visitor sees, and a fresh mtime on every file loses the page dates that search engines read. Server deploys already avoid both with releases and rollback.

## Goal

A deploy to a third-party host (ftp/sftp/ssh) leaves the live folder either fully old or fully new: a stopped or failed upload changes nothing the visitor sees. File times survive the upload, so a served page answers with the date of its built file.

## Acceptance (Given–When–Then)

- Given a target deploy over ftp, sftp or ssh, When the run fails or is stopped mid-upload, Then the live folder still serves exactly the previous content.
- Given a successful target deploy, When it finishes, Then the live folder holds the new files, no staging or old copy stays behind, and each file keeps the time of its local source.
- Given a deployed page, When the Human asks for its headers, Then Last-Modified equals the time of the local file, and docs/usage tells exactly how to check it.

## Out of scope

- Rollback command for targets: the local snapshot under target-backups stays the undo path, as today.
- Atomicity for server deploys: releases and rollback already cover them.
- Brotli and any nginx compression work (HOSTME-IDEA-003).
