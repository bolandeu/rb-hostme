## Problem

On a bare Ubuntu 26.04 box server init leaves the machine without the Let's Encrypt email and without rsync. The first deploy then fails: the certificate step asks for an email and reports a rate-limit notice, and the file transfer dies with rsync: command not found. Worse, after that failed certificate attempt hostme still reports the site as deployed over HTTPS while the certificate is Webinoly's self-signed placeholder, and a later retry cannot recover: the releases layout makes the webroot a symlink, and Webinoly's acme-challenge location runs with disable_symlinks on, so Let's Encrypt gets 404.

## Goal

A machine prepared by server init takes a deploy on the first try: a valid certificate, files transferred, and a deploy that never claims HTTPS while the certificate is a placeholder.

## Acceptance (Given–When–Then)

- Given a bare Ubuntu 26.04 server, When server init runs and a site is deployed, Then the first deploy issues a valid Let's Encrypt certificate and ends with a site that answers over HTTPS. [check: manual]
- Given a site whose certificate is the Webinoly placeholder, When it is deployed, Then the command fails or repairs the certificate, and never reports the site as served over HTTPS. [check: manual]

## Implementation decisions

- Server preparation belongs to server init: the Let's Encrypt contact and the transfer tool are post-conditions of that command, not manual prerequisites.
- A deployed site's success claim includes the certificate: a placeholder certificate is a failed deploy, not a warning.

## Test seams

- The public CLI: server init exit code, deploy exit code and the JSON envelope.

## Out of scope

- Support for a server without root access.
- Wildcard certificates and DNS validation: the manual procedure stays as documented.
