# PRD: Hostme — личный аналог surge.sh

> Название — **hostme**.

Статус: черновик для ревью. Разделы с пометкой **[TBD/уточнить]** нужно проверить/подтвердить перед началом реализации.

---

## 1. Идея и философия

Нравится философия [surge.sh](https://surge.sh/): берёшь папку с сайтом, выполняешь одну команду — сайт уже доступен по URL. Никакого веб-интерфейса, никакой ручной настройки сервера каждый раз, минимум трения между «код готов» и «код доступен по ссылке».

Hostme — это то же самое, но:

- **Полностью личное** — один пользователь (я), никакой регистрации, тарифов, биллинга. Все фичи из платных тарифов surge.sh включены сразу и бесплатно, т.к. инфраструктура своя.
- **Своя инфраструктура вместо облака surge** — сайты раскатываются не на серверы Surge Inc., а на **свои VPS**, которыми я сам владею и администрирую.
- **Деплой не в один сервер, а в любой из нескольких** — можно держать несколько VPS (например, для разных проектов/клиентов) и указывать, куда именно деплоить.
- CLI на **Python + uv**, конфигурация — **YAML**, с возможностью в будущем разнести конфиг на несколько YAML-файлов.
- На сервере должны нормально работать не только статические файлы, но и **простые PHP-скрипты**.

## 2. Пользователь и сценарий использования

Два типа «пользователей», оба — я же, просто разный интерфейс вызова:

1. **Я напрямую**, из терминала на своей рабочей машине (macOS).
2. **Агенты (Claude Code + скиллы)**, которые от моего имени публикуют сайты, страницы или вообще любые артефакты (сгенерированный HTML, отчёт, лендинг, что угодно) на моих же серверах — вместо/в дополнение к публикации через Claude Artifacts. Отсюда требование: CLI должен быть удобен для **неинтерактивного** вызова агентом — предсказуемый вывод, понятные коды возврата, без блокирующих интерактивных промптов по умолчанию (см. раздел 9).

CLI по форме команд намеренно повторяет `surge` (`surge <path> <domain>`, `surge <domain> teardown` и т.п. — см. [surge.sh/docs/cli](http://surge.sh/docs/cli/)), не изобретая свой стиль, и добавляет только то, чего у surge нет по определению — выбор сервера и домена. Типичный сценарий:

```
cd ~/dev/my-landing
hostme . my-landing.example.dev
✔ Deployed to https://my-landing.example.dev
```

Или на конкретный сервер и с собственным доменом:

```
hostme ./dist myclient.com --server vps2
✔ Deployed to https://myclient.com
```

Если домен не указан — как и в surge (там генерится случайный `<word>-<word>.surge.sh`), по умолчанию берётся `<имя-папки>.<первый зарегистрированный служебный домен>`. Служебных доменов может быть сколько угодно (раздел 4), но именно первый когда-либо добавленный через `domain add` — это домен по умолчанию для авто-генерации имени, если не указан явно ни домен, ни `--server`.

Повторный деплой в тот же домен — просто обновляет файлы на месте (идемпотентно, без пересоздания конфигурации).

## 3. Архитектура (верхнеуровнево)

```
┌────────────────────────┐        SSH / rsync        ┌───────────────────────────────┐
│  Локальная машина (Mac) │ ─────────────────────────▶ │  VPS #1 (Ubuntu)               │
│                          │                            │  Webinoly (nginx + php-fpm +   │
│  hostme (CLI, Python/uv) │                            │  certbot) — управляет сайтами   │
│  ~/.config/hostme/*.yaml │                            │  на этом сервере                │
│    - servers.yaml        │                            └───────────────────────────────┘
│    - sites.yaml (+includes)                          ┌───────────────────────────────┐
└────────────────────────┘ ─────────────────────────▶ │  VPS #2 (Ubuntu)               │
                                                         │  Webinoly                      │
                                                         └───────────────────────────────┘
```

Ключевое архитектурное решение: **не писать свой сервер/демон и не генерить nginx-конфиги с нуля**, а опереться на [Webinoly](https://webinoly.com/) ([установка](https://webinoly.com/install/)) — готовый стек на nginx с собственным CLI (`site`, `stack`, `httpauth`, `webinoly`), который уже умеет:

- ставиться одной командой на чистый Ubuntu Server: `curl -sSLf qrok.es/wy -o weby && sudo bash weby <режим>`;
- заводить сайт нужного типа одной командой: `sudo site <domain> -html` (статика) или `sudo site <domain> -php` (PHP через php-fpm);
- выпускать и продлевать SSL (Let's Encrypt) флагом `-ssl=on`, включая wildcard-сертификаты для base-доменов;
- вешать HTTP Basic Auth через `sudo httpauth -add`;
- держать несколько сайтов на одном VPS с изоляцией через nginx server blocks / php-fpm пулы.

Webinoly умеет ставиться в разных режимах (`-nginx` — только nginx, `-php` — nginx+php-fpm без БД, `-lemp` — ещё и MariaDB/MySQL для WordPress, `-clean` — без пакетов). Поскольку **WordPress мы не размещаем** (см. раздел 10) и MySQL/MariaDB пока не нужны (максимум — SQLite на уровне самого PHP-приложения, без отдельного сервера БД), `server init` ставит Webinoly в режиме **`-php`** (nginx + php-fpm, без MySQL) — этого достаточно и для статики, и для простых PHP-скриптов.

`hostme` — это тонкая обёртка: локальный CLI + реестр в YAML + SSH-клиент, который вызывает Webinoly на нужном сервере и заливает файлы rsync'ом. Сам `hostme` не хранит состояние сайта на сервере — источник правды по факту наличия сайта на VPS хранит Webinoly (`site`/nginx-конфиги), а локальный YAML — это удобный реестр «что куда задеплоено» для CLI-команд типа `list`/`open`/`teardown`.

**[TBD/уточнить]** Точный флаг удаления сайта в Webinoly (предположительно `sudo site <domain> -delete`) и поведение install-скрипта в неинтерактивном режиме — сверить с документацией Webinoly (`site`, `stack`, `webinoly` разделы) на этапе реализации `teardown`/`server init`.

## 4. Домены и адресация

Два независимых механизма, оба нужны:

1. **Служебные (base) домены с wildcard** — я регистрирую один или несколько доменов как «служебные» для конкретного сервера (например, `example.dev` → VPS #1, через `hostme domain add vps1 example.dev`). Под ними включается wildcard DNS + wildcard SSL, и под каждым из них можно завести сколько угодно поддоменов-сайтов:
   ```
   hostme ./dist blog.example.dev
   → https://blog.example.dev
   ```
   Сервер для деплоя в этом случае определяется автоматически — по тому, за каким сервером зарегистрирован `example.dev`.
2. **Собственные домены 2-го уровня** — для отдельного сайта можно привязать любой домен, которым я владею, вместо/в дополнение к автоматическому поддомену:
   ```
   hostme ./dist myclient.com --server vps2
   → https://myclient.com
   ```
   `--server` обязателен только при первом деплое домена, который ещё не зарегистрирован ни за одним сервером (`hostme` не может угадать, куда его направить). Также требует, чтобы я вручную направил A/CNAME-запись домена на IP нужного сервера — сам `hostme` DNS у регистраторов не администрирует.

Служебных base-доменов может быть сколько угодно, на одном или разных серверах, и они спокойно соседствуют с кастомными доменами. SSL включён всегда и для всех — как для поддоменов, так и для кастомных доменов, без опции отключить.

**Домен по умолчанию.** Из всех когда-либо зарегистрированных служебных доменов (через `domain add`) первый по порядку добавления считается доменом по умолчанию — именно под ним автогенерируется поддомен, если при деплое не указан ни домен, ни `--server` (раздел 2). Остальные служебные домены равноправны с ним и с кастомными доменами, разница только в этом дефолте для авто-именования.

**Защита от коллизий.** Домен — уникальный ключ сайта в реестре `sites.yaml`. Перед деплоем `hostme` проверяет: если домен уже привязан к *другому* локальному пути — деплой отклоняется с понятной ошибкой (важно и для меня, и для агентов, которые не должны случайно перезаписать чужой сайт тем же доменом); если это повторный деплой *того же* пути в тот же домен — файлы просто обновляются на месте.

## 5. Функциональные требования

Ориентир — фичи free + pro тарифов surge.sh, но без ограничений (всё включено):

| Фича surge.sh | Реализация в Hostme |
|---|---|
| Unlimited publishing / unlimited projects | Нет искусственных лимитов — реестр YAML растёт свободно, серверов и сайтов сколько угодно |
| Custom domain | Домен указывается позиционным аргументом при деплое (см. раздел 4) |
| Basic SSL / Custom SSL | Авто-выпуск и продление Let's Encrypt через Webinoly (`-ssl=on`) на каждом (под)домене; для kастомных случаев — возможность подложить свой сертификат/ключ |
| Force http → https | Флаг при деплое / поле в YAML сайта, реализуется через nginx redirect |
| Cross-Origin Resource Sharing | Поле в YAML сайта со списком origin'ов → добавляется nginx-сниппет с CORS-заголовками |
| Custom redirects | Список `from → to` в YAML сайта → nginx rewrite/return правила |
| Password protection | Сценарий: не публичный доступ — сайт закрыт логином/паролем, и ссылку с паролем можно кому-то отправить, чтобы он один открыл предпросмотр. Реализуется через `httpauth` Webinoly (HTTP Basic Auth) на весь сайт: `hostme <domain> auth --user X --pass Y` / `hostme <domain> auth --off` |
| PHP-скрипты | Через php-fpm (`site <domain> -php`, часть Webinoly); при деплое автоопределение — если в папке есть `*.php`, сайт создаётся как PHP-сайт, иначе как статический (`-html`). WordPress (`-wp`) намеренно не используется — см. раздел 10 |

## 6. CLI-команды

Форма команд намеренно повторяет [surge.sh CLI](http://surge.sh/docs/cli/): `<path> <domain>` для деплоя, `<domain> <подкоманда>` для управления конкретным сайтом. Единственное, чего нет у surge и что добавлено здесь — управление серверами/base-доменами (у surge инфраструктура своя и скрытая, у нас — свои VPS, которые надо явно зарегистрировать) и `--server` там, где домен нужно привязать к конкретной машине. Account-команды surge (`login`, `logout`, `whoami`, `plan`, `card`, `mfa`, `tokens`, `invite`, `revoke`, `nuke`, `stats`) не переносятся — они про SaaS с чужими пользователями и биллингом, здесь не нужны (single user, своя инфраструктура).

**Деплой и управление сайтом** (аналог `surge <path> <domain>` / `surge <domain> <subcommand>`):

- `hostme <path> [domain] [--server NAME]` — деплой/обновление сайта. Если `domain` не указан — берётся `<имя-папки>.<base-домен сервера по умолчанию>` (аналог авто-генерируемого домена в surge). `--server` нужен только при первом деплое ещё не зарегистрированного кастомного домена — для уже известного base-домена сервер определяется автоматически (раздел 4). Тип сайта на Webinoly определяется автоматически (`*.php` в папке → `-php`, иначе `-html`)
- `hostme <domain> teardown` — снести сайт на сервере (через Webinoly) и убрать из реестра
- `hostme <domain> config [--php|--no-php] [--force-https|--no-force-https] [--cors ORIGIN ...] [--redirect FROM=TO ...]` — посмотреть/поменять настройки сайта без передеплоя файлов
- `hostme <domain> auth --user U --pass P` / `hostme <domain> auth --off` — вкл/выкл password protection (см. раздел 5)
- `hostme <domain> ssl [--cert PATH --key PATH]` — SSL включён по умолчанию всегда; команда нужна только для подстановки собственного сертификата вместо Let's Encrypt
- `hostme <domain> debug` — статус (HTTP-пинг) + хвост nginx/php-fpm логов этого сайта с сервера
- `hostme list` — таблица всех сайтов по всем серверам: домен, сервер, php вкл/выкл, ssl, дата деплоя
- `hostme open <domain>` — открыть сайт в браузере

**Серверы и домены** (расширение сверх surge, нужное из-за self-hosted и мульти-сервер/мульти-домен):

- `hostme server add --name vps1 --host 1.2.3.4 --user root [--key ~/.ssh/id_ed25519] [--default]` — зарегистрировать сервер в `servers.yaml`
- `hostme server init vps1` — подключиться по SSH и поставить/проверить Webinoly в режиме `-php` (идемпотентно, см. раздел 3)
- `hostme server list` / `hostme server remove vps1`
- `hostme domain add vps1 example.dev` — зарегистрировать служебный (wildcard) base-домен за сервером

**Phase 3 (пока не в MVP, тоже по образцу surge)**: `hostme <domain> revs`, `hostme <domain> rollback` / `rollfore` / `cutover` / `discard` — история версий и откат (см. раздел 11).

## 7. Конфигурация (YAML)

`~/.config/hostme/servers.yaml`:

```yaml
servers:
  - name: vps1
    host: 45.12.34.56
    user: root
    ssh_key: ~/.ssh/id_ed25519
    default: true
    base_domains:
      - name: example.dev
        default: true    # первый когда-либо добавленный — используется для авто-именования (раздел 4)
  - name: vps2
    host: 88.99.11.22
    user: deploy
    ssh_key: ~/.ssh/id_ed25519
    base_domains:
      - name: side-projects.io
```

`~/.config/hostme/sites.yaml` (основной реестр сайтов, поддерживает подключение дополнительных файлов):

```yaml
include:
  - sites.d/personal.yaml
  - sites.d/clients.yaml

sites:
  - domain: blog.example.dev
    server: vps1
    local_path: /Users/me/dev/blog/dist
    php: false
    ssl: true
    force_https: true
    cors: []
    redirects: []
    password_protect: null
    deployed_at: "2026-09-08T12:00:00"
```

Механизм `include` позволяет со временем разнести сайты по нескольким файлам (например, по проектам или клиентам), не трогая основной файл — то, что было явно нужно на старте.

## 8. Технологический стек

- Python, версия закреплена через **`uv python pin`** (`.python-version` в репозитории) — инструмент не зависит от системного Python
- CLI-фреймворк: **Typer** (подкоманды `server`, `domain`, `redirect`, авто-`--help`)
- YAML: **ruamel.yaml** (сохраняет форматирование/комментарии — конфиг предполагается редактировать руками)
- SSH/rsync: обёртка над системными `ssh`/`rsync` через `subprocess` (уважает `~/.ssh/config`, алиасы и агент — уже используется в текущих привычках работы, а не отдельная Python SSH-библиотека)
- Вывод в терминал: **rich** (таблицы для `list`/`status`)
- На сервере: **Webinoly** (nginx + php-fpm + certbot)

**Установка и конфиг:**

- Исходный код инструмента — этот репозиторий (`static-site-hosting`)
- Установка глобально командой **`uv tool install .`** (или `--editable .` на время разработки) — после этого `hostme` доступен как обычная команда в PATH из любой директории и от имени агентов, без `uv run`
- Все настройки инструмента хранятся в одном месте — `~/.config/hostme/` (`servers.yaml`, `sites.yaml` + `sites.d/*.yaml` из `include`), отдельно от исходного кода репозитория, чтобы личные хосты/домены не утекали в git

## 9. Нефункциональные требования

- Аутентификация — только SSH-ключи, никакой отдельной системы логинов/токенов не нужно (single user).
- Управляющая машина — macOS (текущее окружение); целевые серверы — Ubuntu VPS (требование Webinoly).
- Без веб-интерфейса в v1 — только CLI.
- Деплой должен быть идемпотентным: повторный деплой в тот же домен не ломает существующий конфиг, а обновляет файлы.
- **Дружественность к агентам** (см. раздел 2): по умолчанию ни одна команда не блокируется на интерактивный ввод (пароли/подтверждения — только через флаги); у всех команд есть режим машиночитаемого вывода `--json`; чёткие коды возврата (0 — успех, ненулевой — ошибка с понятным текстом в stderr), чтобы агент мог программно определить результат деплоя.

## 10. Вне скоупа (Non-goals) для v1

- **WordPress** — Webinoly это умеет (`-wp`), но осознанно не используем: не нужен ни сам WordPress, ни MySQL/MariaDB под него.
- MySQL/MariaDB вообще — пока не нужны; если PHP-скрипту нужна БД, максимум SQLite (файловая, без отдельного сервиса).
- Account/биллинг/collaboration-команды surge (`login`, `whoami`, `plan`, `card`, `mfa`, `tokens`, `invite`, `revoke`, `stats`, `nuke`) — это про мультитенантный SaaS с чужими пользователями, здесь не нужны (single user, своя инфраструктура, всё включено по умолчанию).
- Git push-to-deploy / CI-интеграция — возможный Phase 3.
- Автоматическая покупка/настройка DNS у регистраторов.
- Docker/контейнерная изоляция сайтов — полагаемся на модель Webinoly (nginx server blocks + php-fpm pools).
- Файловый watch / автодеплой при сохранении.

## 11. Фазы реализации

**Phase 1 (MVP)** — начинаем с 1 сервера и 1 служебного домена с любым количеством поддоменов, дальше расширяем
- `server add`, `server init` (Webinoly в режиме `-php`) для одного сервера
- один служебный wildcard-домен (`domain add`)
- `hostme <path> [domain]` — деплой статики и PHP-сайтов через Webinoly, с автоопределением типа и защитой от коллизий доменов
- `list`, `open`, `teardown`
- авто-SSL через Webinoly (всегда включён)
- `--json`-вывод и предсказуемые коды возврата для агентов

**Phase 2**
- несколько серверов и несколько служебных доменов
- кастомные домены 2-го уровня (`--server` при первом деплое)
- `auth` (password protection), `config` (CORS, redirects, force-https)
- разбиение `sites.yaml` через `include`

**Phase 3 (возможные доработки)**
- `debug` с реальным опросом сервера (логи + статус)
- `revs` / `rollback` / `rollfore` / `cutover` / `discard` — простой rollback (releases/<timestamp> + symlink `current`, capistrano-style, по образцу surge)
- git push-to-deploy как альтернативный способ деплоя
- `-proxy=` сайты (reverse proxy на Node/etc. через Webinoly), если когда-нибудь понадобится не-PHP приложение
