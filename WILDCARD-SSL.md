# Выпуск wildcard SSL — инструкция (проверено на antagorapp.ru и bolandau.ru)

**2026-09-09, bolandau.ru**: пройдено полностью успешно тем же путём. Единственное отличие от прогона на `antagorapp.ru` — TXT-запись `_acme-challenge.bolandau.ru` распространялась по 6 NS Beget неравномерно и не за один раз: между проверками "не хватает" NS менялся (то `ns1.beget.pro`, то `ns1.beget.com`), несколько минут ушло на ожидание, пока все 6 не показали одно и то же значение подряд. Сертификат подтверждён: SAN содержит `DNS:*.bolandau.ru, DNS:bolandau.ru`, `sudo site bolandau.ru -info` → `SSL: Let's Encrypt`.

Ручная операция на сервере `sites-first-beget` (212.67.13.95), 2026-09-08. Делается руками через SSH, потому что Let's Encrypt для wildcard-сертификатов требует DNS-01 challenge (TXT-запись), а добавлять записи в DNS Beget можно только из панели Beget — API-доступа туда у меня пока нет (см. «Автоматизация» в конце).

**Статус: пройдено полностью и успешно на `antagorapp.ru`.** Сертификат выпущен на `antagorapp.ru` + `*.antagorapp.ru` одним запросом, истекает `2026-12-07`. Ниже — инструкция, уже поправленная по факту реального прогона (изначальный черновик ошибался в паре мест, см. «Что оказалось не так, как думали изначально»).

Исходное состояние на тот момент:
- DNS `antagorapp.ru` → `212.67.13.95`, и `*.antagorapp.ru` уже резолвился туда же (wildcard A-запись в Beget DNS уже стояла) — этот шаг делать не пришлось.
- На сервере не было ни одного сайта (`sudo site -list` → пусто).
- Webinoly 1.21.2 установлен в режиме `-php` (nginx + php-fpm, без MySQL).

## Шаг 1 — зайти на сервер

```
ssh sites-first-beget
```

(алиас уже настроен в `~/.ssh/config`, ключ `bolandau`)

## Шаг 2 — создать сайт-заглушку для базового домена

Webinoly привязывает SSL-сертификат к существующему сайту, поэтому сначала нужен сам сайт:

```
sudo site antagorapp.ru -html
```

## Шаг 3 — (один раз) задать email для Let's Encrypt

Чтобы не отвечать на вопрос про email на каждый чих:

```
sudo webinoly -email=r.bolandau@gmail.com
```

## Шаг 4 — запросить wildcard-сертификат

```
sudo site antagorapp.ru -ssl=on -wildcard
```

Дальше certbot (внутри Webinoly) делает так — **строго последовательно, не одновременно**:
1. Просит email, если не задан на шаге 3.
2. Печатает: `Requesting a certificate for antagorapp.ru and *.antagorapp.ru` — да, это ОДИН сертификат на оба identifier'а сразу (apex + wildcard), но подтверждаются они по очереди.
3. Показывает **первую** DNS TXT-запись под именем `_acme-challenge.antagorapp.ru` и ждёт `Enter`.
4. После `Enter` он **сразу проверяет** эту первую запись (без предупреждения) — если она ещё не разошлась по всем NS, весь запрос целиком проваливается (см. «Что пошло не так в первый раз» ниже), и всё начинается заново с новыми токенами.
5. Если первая запись прошла — печатает **вторую** TXT-запись (то же имя `_acme-challenge.antagorapp.ru`, другое значение) и явно предупреждает: «This must be set up in addition to the previous challenges; do not remove, replace, or undo the previous challenge». То есть на этом шаге в DNS должны стоять **обе** записи одновременно (два TXT-значения на одном имени — это нормально, RFC разрешает).
6. Второй `Enter` → проверка второй записи → `Successfully received certificate`.

## Шаг 5 — добавить первую TXT-запись в панели Beget

Зайди в DNS-настройки домена в панели Beget → добавь TXT-запись ровно с тем именем и значением, что показал Webinoly (`_acme-challenge.<домен>`, если панель сама достраивает домен — просто `_acme-challenge`).

## Шаг 6 — проверить, что запись разошлась по ВСЕМ NS Beget, прежде чем жать Enter

Это самый важный шаг, который в первый раз проигнорировали и словили провал. У Beget домен обслуживают **шесть** неймсерверов тремя кластерами: `ns1/ns2.beget.ru`, `ns1/ns2.beget.pro`, `ns1/ns2.beget.com`. Они синхронизируются не мгновенно — правка в панели какое-то время видна не на всех сразу.

Спроси меня — я проверю **каждый NS по отдельности** (не через публичный резолвер типа 8.8.8.8, а именно `dig ... @ns1.beget.ru`, `@ns2.beget.ru` и т.д. — иначе легко попасть на закэшированный/неактуальный ответ) и скажу, когда все шесть согласны. Только после этого жми `Enter`.

## Шаг 7 — повторить шаги 5–6 для второй записи

Certbot покажет вторую TXT-запись только после того, как примет первую. Добавь её **в дополнение** к первой (не удаляя первую), дождись пока и она разойдётся по всем шести NS (см. шаг 6), и только тогда жми `Enter` второй раз.

## Шаг 8 — проверить результат

```
sudo site -list
sudo site antagorapp.ru -info
```
Должно показать сайт с SSL включённым.

## ⚠️ Важно: wildcard-сертификаты не продлеваются автоматически

Из документации Webinoly: сертификаты с manual/DNS-валидацией (а wildcard — всегда такой) **не продлеваются автоматически**, в отличие от обычных. Через ~90 дней придётся повторить шаги 4–7 (или `sudo site antagorapp.ru -ssl=force-renewal -wildcard`, всё равно с новым DNS TXT challenge).

Это уже отмечено как компромисс в `TODO.md` (2.1) — для MVP по факту может быть проще обойтись без wildcard и выпускать обычный `-ssl=on` на каждый поддомен по отдельности (auto-renew, без ручных шагов), а wildcard оставить на случай, когда понадобится сразу закрыть весь домен без ручной возни per-сайт.

## История: что пошло не так в первый раз

Первая попытка (`sudo site antagorapp.ru -ssl=on -wildcard`) провалилась с ошибкой certbot:

```
Certbot failed to authenticate some domains (authenticator: manual). The Certificate Authority reported these problems:
  Identifier: antagorapp.ru
  Type:   unauthorized
  Detail: Incorrect TXT record "ixIXmtIs..." found at _acme-challenge.antagorapp.ru
  Identifier: antagorapp.ru
  Type:   unauthorized
  Detail: During secondary validation: Incorrect TXT record "kmoVBG2A..." found at _acme-challenge.antagorapp.ru
```

Причина: TXT-запись была добавлена в панели Beget, но **разошлась не по всем NS одновременно** — primary- и secondary-проверки Let's Encrypt (это два разных сетевых vantage point, стандартная защита LE от BGP-хайджека) увидели два разных значения, потому что часть NS-кластеров Beget (`ns1/ns2.beget.ru`, `.pro`, `.com`) на тот момент ещё отдавала старое/другое значение. Проверка через публичные резолверы (8.8.8.8, 1.1.1.1) в моменте *не помогла* — они тоже могут закэшировать один конкретный ответ и не показать реальный разнобой между NS.

Урок, который лёг в шаг 6 выше: проверять **каждый из шести NS Beget напрямую** (`dig TXT ... @ns1.beget.ru` и т.д.), а не полагаться на локальный/публичный резолвер.

Вторая попытка (уже с проверкой по всем NS перед каждым `Enter`) прошла успешно с первого раза.

## Автоматизация (сделать позже)

Весь этот процесс — кандидат на автоматизацию через API хостинга/регистратора, чтобы `hostme domain add`/`hostme server init` могли выпускать wildcard-сертификат без ручных TXT-записей (см. `TODO.md`, раздел 2.1). Что уже известно на эту тему:

- Пробовал API Beget (`https://api.beget.com/api/domain/getList`) с переданными логином/паролем — получил `AUTH_ERROR: Username/password incorrect` и на GET, и на POST. Значит, для автоматизации нужны **рабочие** креды (перепроверить логин/пароль в панели Beget) и, скорее всего, отдельный API-метод для управления DNS-записями домена (не `domain/getList`, а что-то вроде `domain/changeRecords` — уточнить по документации Beget API при возврате к этой задаче).
- Если/когда API-доступ появится, автоматизация сведётся к: certbot `--manual` с `--manual-auth-hook`/`--manual-cleanup-hook` скриптами, которые сами кладут/удаляют TXT-запись через API Beget — тогда весь ручной процесс из этого файла исчезает, и `hostme` сможет дергать это программно (в т.ч. на автопродление, которое сейчас в принципе недоступно для wildcard в Webinoly без такого hook'а).
- До тех пор — **wildcard остаётся ручной операцией** по этой инструкции, а в MVP (Phase 1, TODO.md) практичнее не полагаться на wildcard вообще и выпускать обычные `-ssl=on` сертификаты на конкретные поддомены (они продлеваются автоматически).
