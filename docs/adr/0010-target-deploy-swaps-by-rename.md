# Деплой на target (ftp/sftp): заливка в staging и подмена rename'ом

Заливка на сторонний хостинг идёт в соседнюю папку `<remote_path>.hostme-staging`,
и только после её успеха живой путь меняется двумя rename'ами в той же родительской
папке: live → `<remote_path>.hostme-old`, staging → live. Прерванная заливка не
трогает живой путь, поэтому посетитель видит либо весь прежний сайт, либо весь новый.

## Статус

accepted

## Варианты

1. **Zаливка по месту с `--delete`** (прежнее поведение, ADR 0006 для ssh-пути).
   Просто и один сеанс lftp, но падение на середине оставляет сайт смешанным:
   часть файлов новая, часть старая, удалённые файлы ещё на месте.
2. **Staging + rename** (выбрано). Две-четыре сеанса lftp вместо одного, зато
   живой путь меняется только целым каталогом.
3. **Releases и симлинк на сервере** (как Webinoly на своих VPS). Нужен shell на
   хостинге; у shared-хостингов его часто нет, а FTP не умеет симлинки.

## Последствия

- Первый деплой: живого каталога ещё нет, `mv live old` падает — это не ошибка,
  staging просто переименовывается в live.
- Второй rename не прошёл — `old` возвращается на место live, наружу уходит
  `FtpError`. Сайт не пропадает и не остаётся пустым.
- После подмены `old` удаляется; не удалось — остаток уберёт начало следующего
  деплоя (обе папки чистятся перед заливкой).
- `remote_path` обязан указывать на каталог: корень аккаунта переименовать нельзя,
  поэтому `remote_path: /` — ошибка аргументов с подсказкой задать подкаталог.
- Соседние папки нужны потому, что rename на хостинге работает только внутри одной
  родительской папки (и обычно только в одной файловой системе).
- Скрипт lftp по-прежнему идёт на stdin: пароль не попадает в argv. Время файла
  берётся с сервера (`ftp:use-mdtm`, `ftp:use-site-utime2`), `--ignore-time` не используется.
- ssh-путь target'а не меняется: там rsync, ADR 0006 остаётся в силе.
