# Готовые nginx-сниппеты для `hostme <domain> config --nginx-snippet`

Заготовки под конкретные требования разных статических генераторов —
заливаются на сайт командой:

```
hostme <domain> config --nginx-snippet docs/nginx-snippets/<файл>.conf
```

Убрать сниппет: `hostme <domain> config --no-nginx-snippet`.

## Прежде чем писать новый — проверить, что Webinoly уже даёт по умолчанию

Не дублировать, иначе просто мёртвый код в сниппете:

- **gzip** — включён глобально (`nginx.conf`)
- **Заголовки** `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Strict-Transport-Security` (HSTS) — уже стоят (`common/headers-*.conf`)
- **Кэш статики** (картинки/шрифты/css/js по расширению) — `expires max` +
  `Access-Control-Allow-Origin: *` уже в отдельном `location` у Webinoly
- **HTML** — `Cache-Control: no-cache` уже стоит

Реально не хватает обычно только: чистых URL (Apache `RewriteRule` их обычно
даёт из коробки через `.htaccess`, у nginx — нет), кастомного `error_page 404`,
и специфичных для конкретного сайта вещей (proxy_pass для API-путей и т.п.).

## Технические ограничения (см. AGENTS.md/docs/webinoly.md)

- Сниппет живёт на уровне `server{}`, **не в своём `location /`** — Webinoly
  уже объявил `location /` в основном конфиге сайта, второй в этом же
  server-блоке уронит `nginx -t`. Логику в стиле try_files можно только через
  именованные `location @foo { ... }` (не участвуют в обычном URI-матчинге).
- `hostme` сам делает `nginx -t` перед `reload` и откатывает файл при поломке
  конфига — синтаксическая ошибка в сниппете никогда не попадёт в работающий
  nginx, но и не подскажет, что именно не так, кроме текста ошибки от `nginx -t`.
- **PHP-сайты (`index index.php ...`, есть `.php`-файлы в проекте) устроены
  иначе, чем чистый HTML**: `location /` у Webinoly делает
  `try_files $uri $uri/ /index.php$is_args$args`. Два следствия:
  1. Промах на статический файл не даёт 404 сразу, а уходит в PHP-location, и
     уже там (`try_files $uri =404` на несуществующий `/index.php`) рождается
     настоящая ошибка. К этому моменту `$uri` **уже переписан** в `/index.php`
     — исходный путь брать из `$request_uri` (единственная переменная,
     которая гарантированно не меняется на внутренних редиректах), а не из
     `$uri`/своей `set`-переменной, захваченной "заранее" — она тоже успеет
     измениться, потому что rewrite-фаза прогоняется заново на каждый
     внутренний redirect.
  2. Если рядом с `page.html` существует одноимённая директория `page/`
     (частый случай — генераторы кладут туда пагинацию/подстраницы, а сама
     `page/index.php` — просто заглушка вида `header('Location: /'); exit;`,
     чтобы не отдавать листинг), `try_files $uri $uri/ ...` матчит
     **директорию раньше файла** — `/page` без слэша получает от Webinoly
     редирект на `/page/`, а `/page/` через `index.php`-заглушку редиректит
     на `/`, а не показывает `page.html`. Решается проактивной проверкой
     `-f $document_root$path.html` на rewrite-фазе (см. `static-site-generator.conf`) —
     она перехватывает запрос ДО того, как Webinoly вообще пробует директорию.
- **`if` вместе с `try_files` в одном `location` не работает** — классическая
  "if is evil" ловушка nginx: `try_files` молча проваливается в fallback,
  даже если искомый файл реально существует. `if`/`set` — только на уровне
  `server{}` (не внутри `location`); в location с `try_files` — только чистый
  `try_files`, без единого `if`.
- **Нельзя объявить `error_page 404` дважды в одном контексте** (второе
  перекрывает первое) **и nginx не перезапускает `error_page` для ошибки,
  возникшей внутри уже активной обработки другого `error_page`** (защита от
  циклов). Из-за этого нельзя было в ОДНОМ location одновременно и пробовать
  `<path>.html`-фолбэк, и (при неудаче) показать кастомную `/404.html` с
  правильным статусом 404 — try_files, найдя `/404.html`, всегда отдаёт его
  как обычный успешный ответ (200), а второй `error_page` для форс-статуса не
  срабатывает. **Решение**: развести на два НЕЗАВИСИМЫХ, невложенных шага —
  проактивная `-f`-проверка (см. пункт про PHP выше) решает вообще ВСЕ случаи,
  когда `<path>.html` существует, ещё до того, как случается любая ошибка;
  а `error_page 404 /404.html; location = /404.html { internal; }` —
  стандартный документированный паттерн nginx, используется только на
  единственном оставшемся случае "файла точно нет", и корректно сохраняет
  статус 404 клиенту, раз ему больше не приходится ни с чем конкурировать.

## `static-site-generator.conf`

Профиль под «Static Landing Generator» (`~/Projects/sitegenerator`, PHP-генератор
статических лендингов — см. его README.md). Полностью проверено вживую на
`test.bolandau.ru` (2026-09-09, реальный проект `mwlogistics` из этого
генератора: PHP+HTML, формы `form.php`/`subscribe.php`, коллизии
`catalog.html`+`catalog/`, `blog.html`+`blog/`). Делает:

- `/page.html` → редирект 301 на `/page`
- `/page/` → редирект 301 на `/page` (кроме корня)
- `/page` → отдаёт `page.html`, если он есть — **включая случаи, когда рядом
  есть одноимённая директория** (`/catalog`, `/blog` у этого проекта)
- Настоящий 404 (статус 404, не 200) с кастомной `/404.html`, если ни файла,
  ни `.html`-версии нет
- PHP-скрипты и статика (картинки/css/js) не затронуты — работают как обычно

Источник вдохновения — `apache-htaccess.conf` из `sitegenerator`
(генератор статики с `.html`-файлами и чистыми URL).
