# Готовые nginx-сниппеты для `hostme <domain> config --nginx-snippet`

Заготовки под конкретные требования разных статических генераторов —
заливаются на сайт командой:

```
hostme <domain> config --nginx-snippet docs/nginx-snippets/<файл>.conf
```

Убрать сниппет: `hostme <domain> config --no-nginx-snippet`.

## Прежде чем писать новый — проверить, что Webinoly уже даёт по умолчанию

Не дублировать, иначе просто мёртвый код в сниппете:

- **gzip** — включён глобально (`nginx.conf`)
- **Заголовки** `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Strict-Transport-Security` (HSTS) — уже стоят (`common/headers-*.conf`)
- **Кэш статики** (картинки/шрифты/css/js по расширению) — `expires max` +
  `Access-Control-Allow-Origin: *` уже в отдельном `location` у Webinoly
- **HTML** — `Cache-Control: no-cache` уже стоит

Реально не хватает обычно только: чистых URL (Apache `RewriteRule` их обычно
даёт из коробки через `.htaccess`, у nginx — нет), кастомного `error_page 404`,
и специфичных для конкретного сайта вещей (proxy_pass для API-путей и т.п.).

## Технические ограничения (см. AGENTS.md/docs/webinoly.md)

- Сниппет живёт на уровне `server{}`, **не в своём `location /`** — Webinoly
  уже объявил `location /` в основном конфиге сайта, второй в этом же
  server-блоке уронит `nginx -t`. Если нужна логика в стиле try_files —
  использовать именованные `location @foo { ... }` (не участвуют в обычном
  URI-матчинге, вызываются только явно через `error_page`/`try_files`).
- `hostme` сам делает `nginx -t` перед `reload` и откатывает файл при поломке
  конфига — синтаксическая ошибка в сниппете никогда не попадёт в работающий
  nginx, но и не подскажет, что именно не так, кроме текста ошибки от `nginx -t`.
- **PHP-сайты (`index index.php ...`, есть `.php`-файлы в проекте) устроены
  иначе, чем чистый HTML**: `location /` у Webinoly делает
  `try_files $uri $uri/ /index.php$is_args$args` — промах на статический файл
  не даёт 404 сразу, а уходит в PHP-location, и уже там (`try_files $uri =404`
  на несуществующий `/index.php`) рождается настоящая ошибка. К этому моменту
  `$uri` **уже переписан** в `/index.php` — если нужен оригинальный
  запрошенный путь (для чистых URL), брать из `$request_uri` (единственная
  переменная, которая гарантированно не меняется на внутренних редиректах),
  а не из `$uri`/`set`-переменной, захваченной заранее — она тоже успеет
  измениться, потому что rewrite-фаза прогоняется заново на каждый внутренний
  redirect.
- **`if` вместе с `try_files` в одном `location` не работает** — классическая
  "if is evil" ловушка nginx: `try_files` молча проваливается в fallback,
  даже если искомый файл реально существует. Если нужен `if`/`set` для
  вычисления пути, который потом пойдёт в `try_files` — делать `if` на
  уровне `server{}` (не внутри `location`), а в самом `location` с
  `try_files` — только чистый `try_files`, без единого `if`.
- **Нельзя объявить `error_page 404` дважды в одном контексте** — второе
  объявление молча перекрывает первое, это не "цепочка". И даже если развести
  их по разным `location`, **nginx не запускает `error_page` повторно для
  ошибки, возникшей внутри уже активной обработки другого `error_page`**
  (защита от бесконечных циклов) — из-за этого не получилось одновременно
  отдать кастомную `/404.html` и сохранить правильный HTTP-статус 404 (см.
  `clean-urls.conf` — там `/404.html` отдаётся клиенту с верным контентом, но
  статусом 200, это осознанный компромисс, не баг).

Все три пункта выше стоили нескольких часов живой отладки на `test.bolandau.ru`
2026-09-09 — не наступать снова.

## `clean-urls.conf`

Проверено вживую на `test.bolandau.ru` (2026-09-09, реальный PHP+HTML
проект с формами на `form.php`/`subscribe.php`). Делает:

- `/page.html` → редирект 301 на `/page`
- `/page` (без файла на диске) → отдаёт `page.html`, если он есть
- Кастомная `/404.html` при отсутствии и `page`, и `page.html` — **статус
  ответа 200, не 404** (известное ограничение, см. выше)
- PHP-скрипты и статика (картинки/css/js) не затронуты — работают как обычно

**Чего сознательно нет**: редиректа `/page/` → `/page` (убрано — зацикливалось
с нативным поведением nginx «директория без слэша → добавить слэш», если
рядом с `page.html` существует одноимённая директория `page/`, частый случай
у генераторов с пагинацией/подстраницами).

Источник вдохновения — `apache-htaccess.conf` из `sitegenerator`
(генератор статики с `.html`-файлами и чистыми URL).
