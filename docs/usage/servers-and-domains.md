# Серверы, домены и деплой

Как файлы доходят до сайта и кто чем владеет.

## Устройство

```text
Mac (ты или агент)                      VPS #1 (Ubuntu + Webinoly)
  hostme <path> <domain>  ──SSH/rsync──▶  nginx + php-fpm + certbot
  ~/.config/hostme/                       сайты, SSL, Basic Auth
  user_data_dir("hostme")/         VPS #2 (Ubuntu + Webinoly) — так же
```

hostme — тонкая обёртка: локальный CLI, реестр в YAML и вызовы Webinoly по SSH.
**Факт наличия сайта на сервере хранит Webinoly** (`site`/nginx-конфиги), а
локальный реестр — это «что куда задеплоено» для `list`, `open`, `teardown`.
Реестр и сервер расходятся — прав сервер.

Сервером управляет Webinoly: свой сервер и свои nginx-конфиги с нуля hostme не
пишет. Почему так — ADR
[0001](../adr/0001-webinoly-manages-the-servers.md).

## Сервер

Сервер — свой VPS с Webinoly. `hostme server add` записывает его в реестр,
`hostme server init` ставит Webinoly в режиме `-php` (nginx + php-fpm, без
MySQL), `hostme server update` обновляет сам Webinoly.

Режим `-php` выбран потому, что MySQL/MariaDB и WordPress не нужны, а статику и
PHP он покрывает полностью.

Требования к машине до `server add` (Ubuntu LTS, порты, SSH-ключ, sudo без
пароля) — раздел «Требования к серверу» в [README](../../README.md).

## Служебные (base) домены

Служебный домен — домен, зарегистрированный за сервером (`hostme domain add`).
Под ним включается wildcard DNS и wildcard SSL, и под ним заводится сколько
угодно поддоменов-сайтов:

```text
hostme ./dist blog.example.dev     → https://blog.example.dev
```

Служебных доменов может быть сколько угодно, на одном сервере или на разных.
Сервер деплоя hostme выбирает по порядку: `--server` → домен уже известен в
реестре сайтов → суффикс base-домена.

**Домен по умолчанию.** Если при деплое не указан ни домен, ни `--server`,
домен генерируется: `<slug(имя-папки)>.<домен по умолчанию>`. Домен по
умолчанию — тот base-домен, у которого стоит флаг `default`: его получает
первый добавленный домен, сменить — `hostme domain default <domain>`. Не-ASCII
имя папки кодируется в punycode (`под-проект` → `xn--…`), потому что DNS и
Let's Encrypt понимают только ASCII.

## Собственные домены 2-го уровня

```text
hostme ./dist myclient.com --server vps2   → https://myclient.com
```

`--server` обязателен только при первом деплое домена, который ещё ни за одним
сервером не закреплён: hostme не может угадать, куда его направить. A/CNAME
человек ставит у регистратора сам.

## Защита от коллизий

Домен — уникальный ключ сайта в реестре. Если домен уже привязан к **другому**
локальному пути, деплой отклоняется с понятной ошибкой (агент не должен
перезаписать чужой сайт тем же доменом). Повторный деплой того же пути в тот же
домен — обычное обновление.

## Что делает деплой

1. hostme находит сервер по домену (или берёт `--server`).
2. Webinoly заводит сайт нужного типа (`-html` или `-php`), если его нет.
3. Файлы заливаются `rsync --delete`: webroot на сервере становится точным
   зеркалом локальной папки на момент деплоя. Если файл убрать из папки, после
   следующего деплоя его нет и на сервере. `--delete` не отключается — почему,
   ADR [0006](../adr/0006-rsync-delete-mirrors-the-server.md).
4. Права на файлы приводит `www-data` — иначе nginx отдаёт 403.
5. SSL выпускается и продлевается сам (Let's Encrypt через Webinoly).

Деплой идемпотентен: повторный деплой той же папки приводит сервер к одному и
тому же состоянию. Обратная сторона зеркала: деплой не той (пустой, неверной)
папки снесёт содержимое сайта.

Сайт на своём сервере живёт в `releases/<метка>/`, а `htdocs` — симлинк на
текущий релиз. Отсюда `revs`, `rollback`, `rollfore` и `maintenance`: старая
версия не теряется до чистки.

## SSL

SSL включён всегда и на каждом домене: и на поддомене, и на собственном домене.
Опции «выключить SSL» нет. Wildcard-сертификат для base-домена выпускается
вручную через DNS-01 (автоматизация — идея HOSTME-IDEA-006); новые поддомены
привязываются к уже выпущенному wildcard без DNS-шага.

## Target — сторонний хостинг

Target — чужой хостинг (ftp, sftp или ssh), зарегистрированный через
`hostme target add`. Это только заливка файлов, без Webinoly: SSL, домены и
конфигурацию сервера держит хостер.

- У target нет base-доменов: домен при деплое указывается явно.
- `auth`, `config`, `debug`, `revs`, `rollfore` не работают — они
  Webinoly-специфичны.
- `rollback` откатывает на последний локальный снепшот сайта, снятый перед
  деплоем (`target-backups/`, политика хранения — `settings.yaml`).
- Деплой, `teardown` и `rollback` на target требуют `--confirm` на каждый
  вызов: это чужая инфраструктура, и `--json` подтверждение молча не
  пропускает.
